# Daily Product Factory Proof

This feature turns AI Product Factory into a continuously evidenced product-building system instead of relying on static marketing claims.

## What runs every day

At **08:00 Asia/Kolkata** GitHub Actions runs the current application from `main` and:

1. Fetches recent public problem signals from multiple sources.
2. Ranks the problem statements using pain/effort language, detail, and engagement.
3. Selects one problem and converts it into a concrete product request.
4. Sends that request through the existing Product Intelligence flow.
5. Runs the existing Deep Research V12 source qualification.
6. Runs the Manager/recommendation gate.
7. If the research gate passes, approves the selected strategy and locks the selected source repositories.
8. Calls the existing approved build endpoint.
9. Records product details, selected repositories, architecture/build verification, and the final claim status.
10. Commits a dated Markdown report plus `latest.json` into `proof/daily/` and uploads the same evidence as a workflow artifact.

The workflow can also be started manually with an optional product idea override.

## Public problem sources

The runner currently uses public, read-only endpoints for:

- Hacker News / Ask HN signals
- Stack Overflow questions
- GitHub Issues

The report stores only a short evidence excerpt and the original source URL. It does not copy full posts or discussions.

## Evidence statuses

### `VERIFIED_END_TO_END`

This is the only status that permits an end-to-end product-build claim. It requires all of the following from the current build response:

- approved repository lock
- product generated
- capability graph built
- starter blueprint generated
- architecture generated
- pipeline completed
- `pipelineVerified: true`

A dated report may then state that AI Product Factory took that cited public problem through research, plan selection, approval, and a pipeline-verified source-locked build.

### `VERIFIED_GUARDRAIL`

The public problem was processed, but the current research gate did not have enough qualified evidence to authorize a build. This is considered correct guardrail behavior. The workflow explicitly does **not** claim that a product was built end to end.

### `FAILED`

The runtime, source discovery, API flow, or build verification failed unexpectedly. The report contains the failure and no product-build claim is published.

## Why this makes the Product Factory claim stronger

The stronger claim is not “we are the best” or “100% accurate.” Those comparisons require a separate benchmark against named alternatives.

What this system can prove is more useful:

> **Evidence-backed product creation:** a real public problem can be traced through discovery, research, source selection, approval, build generation, and executable verification using the current Product Factory code.

Every successful day produces a dated proof record. Failed or insufficient-research days remain visible instead of being hidden, which makes the evidence more credible.

## Generated report contents

Each dated report includes:

- final status and claim text
- number of source sites reached
- number of problem candidates ranked
- chosen problem statement, excerpt, and source URL
- exact product request sent into the factory
- customer goal and selected product plan
- recommendation quality and research-gate status
- selected source repositories with reasons
- build verification checklist
- top alternative problem candidates
- source-discovery health
- any runtime/build error

`proof/daily/latest.json` provides the same key evidence in machine-readable form for a future website badge, dashboard, API, or README widget.

## Files

- `.github/workflows/daily-product-proof.yml` — scheduled/manual workflow
- `scripts/daily-product-proof.mjs` — discovery, factory execution, evidence and report generation
- `proof/daily/YYYY-MM-DD.md` — dated proof generated by the workflow
- `proof/daily/latest.json` — latest machine-readable proof

## Optional next step

A public “Proof of Build” page can read `proof/daily/latest.json` and show the latest verified product, source problem, research score, repositories, and pipeline checks directly in the Product Studio UI. That should display the same status rules above and must never convert a guardrail or failed run into a success claim.
